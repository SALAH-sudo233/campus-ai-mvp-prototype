# 0005 组织与角色模型

状态：已接受
日期：2026-11-20（2026-11-26 按 #28 扩展为四端五角色）

## 背景

现有原型只有学生和管理员两身份，账户、流水和密钥都围绕 `owner_ref`。试点要支持平台、组织、成员三层结构，同时保持旧客户端可用。

2026-11-26 的 #28 决定采用四端、五角色。学生使用 `org_member`；校内运营使用 `org_operator`；学院观察员使用 `college_viewer`，服务端强制只读；平台使用 `platform_admin`。`org_admin` 保留为兼容上级名称，当前拥有与 `org_operator` 相同的本组织运营权限，不获得平台管理权限。

## 决策

### 层级

```text
平台管理员（platform_admin）
└── 组织
    ├── 组织管理员（org_admin，兼容上级）
    ├── 校内运营（org_operator）
    ├── 学院观察员（college_viewer，只读）
    └── 组织成员（org_member，学生）
```

组织是权限边界。用户可以属于多个组织，每个组织内的角色单独保存。平台管理员在组织之上，不放进组织的成员列表。

### 角色

| 角色 | 范围 | 说明 |
|---|---|---|
| `platform_admin` | 全平台 | 创建组织、管理组织内角色和准入、导入各类组织角色、批量分配额度、执行现有结算并查看审计 |
| `org_admin` | 本组织 | 兼容上级名称，当前继承 `org_operator` 的全部权限；不授予角色管理、直接发额度或结算权限 |
| `org_operator` | 本组织 | 查看成员与用量、审核准入、导入学生、审核作品、精选和下架；不能把导入或创建成员作为提权入口 |
| `college_viewer` | 本组织 | 读取学院汇总、趋势、看板、已发布作品和奖励概况；所有受保护写动作返回 403 |
| `org_member` | 本人及本组织公开作品 | 查看本人账户、使用自己的额度和密钥、提交及撤回作品、点赞和评论 |

组织配置继续提供 `admin_label` 和 `member_label`。授权统一使用服务端 authz 矩阵中的角色、资源、动作和作用域，不按显示名称或前端页面判断。CMS 和发奖申请的业务入口由后续任务实现，本次不新增这些入口。

### 数据

| 表 | 作用 |
|---|---|
| `organizations` | 组织、slug、状态和显示文案 |
| `users` | 不随登录方式变化的用户主体 |
| `user_identities` | 学号、邮箱等登录身份 |
| `org_memberships` | 用户在组织内的角色、准入状态和外部编号 |
| `org_policies` | 组织级趋势天数等策略 |
| `audit_events` | 操作审计，不含密钥明文 |

`students`、`ledger`、`sessions` 和中转站台账增加 `user_id`、`org_id`。旧 `owner_ref` 保留，旧接口继续按它查询。

### 权限

权限矩阵在服务端维护，按角色、资源和动作判断。跨组织请求统一返回 403，不区分资源不存在和无权访问。前端隐藏按钮不作为授权依据。

学院观察员的矩阵只包含读取动作。PAT 创建、PAT 撤销、点赞和评论分别使用独立写动作，不复用个人信息或作品读取权限。运营端创建成员、名单预览和名单确认都检查目标角色；创建或导入非学生角色需要平台的角色管理权限。

演示账户属于独立演示组织，不改变真实学院的名册、配额或统计。demo 限制在主体装配时保持一致，签发 PAT 也不能绕过不发真实 Key 的约束。演示平台主体不得重置真实数据，拒绝结果追加到审计记录。

名单导入遇到学号或邮箱已属于其他组织时判为身份冲突，不自动并入。同一人跨组织归属需要后续的显式邀请或身份核验流程，首期未实现。

密钥明文只在发放响应出现一次。组织管理员只能读取掩码，平台管理员也不能二次读取明文。

## 后果

- 旧学生接口的字段和幂等行为保持不变。
- 旧 teacher 演示登录兼容映射到 `org_operator`。`college_viewer` 是独立的学院观察员角色，不能因访问运营页面或直接调用 HTTP 获得写权限。旧库真实 `org_admin` 记录保留，不删除或重写真实账户。
- 新组织只需新增组织、成员和策略数据，不复制页面逻辑。
- 邮箱账户和学号账户仍可能对应两个 `owner_ref`，但可以关联到同一个用户主体。
