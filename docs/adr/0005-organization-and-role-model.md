# 0005 组织与角色模型

状态：已接受
日期：2026-11-20

## 背景

现有原型只有学生和管理员两身份，账户、流水和密钥都围绕 `owner_ref`。试点要支持平台、组织、成员三层结构，同时保持旧客户端可用。

调研稿曾把教师列为独立的只读角色。用户已决定教师就是组织管理员，组织内只保留组织管理员和组织成员两种角色。

## 决策

### 层级

```text
平台
└── 组织
    ├── 组织管理员（试点显示为教师）
    └── 组织成员（试点显示为学生）
```

组织是权限边界。用户可以属于多个组织，每个组织内的角色单独保存。平台管理员在组织之上，不放进组织的成员列表。

### 角色

| 角色 | 范围 | 说明 |
|---|---|---|
| `platform_admin` | 全平台 | 创建组织、查看全部组织与审计、批量分配额度、全局下架作品 |
| `org_admin` | 单一组织 | 查看本组织全部成员姓名、学号、用量和密钥掩码，导入名单、审核作品、精选和下架 |
| `org_member` | 单一组织 | 查看自己的额度、流水、密钥和作品，提交与撤回自己的作品 |

组织配置提供 `admin_label` 和 `member_label`。试点组织把它们设为“教师”和“学生”。代码按角色判断，不按中文称呼判断。

### 数据

| 表 | 作用 |
|---|---|
| `organizations` | 组织、slug、状态和显示文案 |
| `users` | 不随登录方式变化的用户主体 |
| `user_identities` | 学号、邮箱等登录身份 |
| `org_memberships` | 用户在组织内的角色、准入状态和外部编号 |
| `org_policies` | 组织级趋势天数等策略 |
| `audit_events` | 操作审计，不含密钥明文 |

`students`、`ledger`、`sessions` 和中转站台账增加 `user_id`、`org_id`。旧 `owner_ref` 保留，旧接口继续按它查询。

### 权限

权限矩阵在服务端维护，按角色、资源和动作判断。跨组织请求统一返回 403，不区分资源不存在和无权访问。前端隐藏按钮不作为授权依据。

名单导入遇到学号或邮箱已属于其他组织时判为身份冲突，不自动并入。同一人跨组织归属需要后续的显式邀请或身份核验流程，首期未实现。

密钥明文只在发放响应出现一次。组织管理员只能读取掩码，平台管理员也不能二次读取明文。

## 后果

- 旧学生接口的字段和幂等行为保持不变。
- 教师端就是组织管理员端加教学展示模块，不再实现第二个只读教师角色。
- 新组织只需新增组织、成员和策略数据，不复制页面逻辑。
- 邮箱账户和学号账户仍可能对应两个 `owner_ref`，但可以关联到同一个用户主体。
